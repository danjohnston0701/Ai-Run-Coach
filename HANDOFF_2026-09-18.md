## 5. Google Play subscription lifecycle — DONE (2026-09-18, second session), verified, uncommitted

**The gap it closes:** a cancelled Play subscriber kept `lite`/`standard` forever — no RTDN endpoint,
`verify-purchase` trusted the client `productId` and guessed `entitlement_expires_at = now + 1 period`,
no token → user mapping, nothing enforced the date. (Apple was already handled by
`server/apple-server-notifications.ts`.)

**What was built (server, no new npm deps):**
- `server/google-play-billing.ts` — service-account OAuth (RS256 JWT via `jsonwebtoken` →
  `oauth2.googleapis.com/token`, cached), `fetchSubscriptionV2()` (`purchases.subscriptionsv2.get`;
  404/410/"token not found" → `null`, other errors → `GooglePlayApiError`), `applySubscriptionState()`
  (upserts `google_play_transactions`, marks `linkedPurchaseToken` predecessors expired; ACTIVE /
  IN_GRACE_PERIOD / CANCELED-with-future-expiry → grant with the **real** expiry; EXPIRED / ON_HOLD /
  PAUSED / unknown token → clear tier + `expired` (or `refunded` when revoked) — but only if the user's
  `entitlement_type` is `google_play_*` and no *other* Play token of theirs is still live, so Apple /
  promo entitlements and upgrade/resubscribe flows are never clobbered; PENDING → no-op),
  `verifyAndApplyPurchase()`, `handleRtdnMessage()`, `reconcileGooglePlaySubscriptions()`.
- `server/routes-google-play.ts` — `POST /api/google/play-notifications` (Pub/Sub push, no user auth,
  optional `?token=` checked against `RTDN_SHARED_SECRET`). 204 acks; `GooglePlayApiError` → 503 so
  Pub/Sub redelivers; anything else is acked and left to the reconcile.
- `server/routes.ts` — mounts the router; `verify-purchase` now delegates to `verifyAndApplyPurchase()`.
  With the service account configured it verifies with Google; a token Google doesn't recognise →
  400 "could not be verified" (refuses to grant, never revokes on a lookup miss). Without the key it
  falls back to the old trust-the-client behaviour (with a warning) but still records the token.
  Response gained `entitled` + `subscriptionState`; `tier` reflects the DB when not entitled.
- `server/scheduler.ts` — hourly (`:15`) reconcile: (1) recorded tokens still in an entitled state
  whose `expiry_time` has passed → re-fetch + apply; (2) users still `active` on `google_play_*` past
  `entitlement_expires_at` → verify via their latest token, or, **with no token on file, clear after a
  3-day grace** (`UNVERIFIABLE_EXPIRY_GRACE_MS`) — the pre-RTDN guessed date was refreshed on every
  app open, so this only hits people who haven't opened the app for >1 period + 3 days; the next app
  open re-verifies and restores if still subscribed. No-ops until the key is configured.
- `server/auto-migrate.ts` + `migrations/20260918_google_play_transactions.sql` — the table
  (`purchase_token UNIQUE`, `user_id` FK cascade, `product_id`, `package_name`, `linked_purchase_token`,
  `expiry_time`, `auto_renewing`, `subscription_state`, `last_checked_at`). Auto-created on server start;
  **already created in Neon** during testing (idempotent).

**Android** (`:app:compileDebugKotlin` clean): `BillingManager.kt` now injects `SessionManager` and sets

## 5b. "AI Plans not included" upsell instead of a raw server error — DONE both platforms + server

Reported (iOS, likely Android too): a free-trial user tapping Generate on an AI Coaching Plan saw
`Server error (429): {"error":"monthly_limit_reached"…}`. Root causes: (1) the server treated a
zero allowance as a "monthly limit reached" (`0 of 0 used, resets next month`); (2) the pre-check
gate (`/api/features/trainingPlansGenerated/available`) isn't on every path into the form
(iOS Profile → Coaching Programme → Create plan; Android Goals → Generate plan for goal) and fails
open on any network error; (3) neither client handled the generate call's own 402/403 refusals.

- **Server** `usage-service.ts`: `limit === 0` now returns **403 `ai_plans_not_included`** (or
  `feature_not_included` for other features) with `reason: "free_trial" | "not_in_tier"`, a
  verbatim-showable `message`, `upgradeRequired: true`. The `ai_plans_enabled=false` branch sends
  the same code with `reason: "ai_plans_excluded"`, so clients treat free-trial and paid-no-AI-Plans
  identically. `FEATURE_LABELS` shared; `/api/features/:feature/available` gained `notIncluded` +
  `reason` and human-readable messages. Verified with a scratch harness (trial → 403 free_trial,
  expired → 402, lite-noai → 403 ai_plans_excluded, standard → allowed).
- **Android**: `GeneratePlanViewModel.parseLimitError()` handles 402/403/429 →
  `LimitReached(notIncluded, reason)`; `GeneratePlanScreen` renders `AiPlanLimitUpsellScreen`
  **full-screen** (Back → form, data kept; Upgrade → `"subscription"` route — previously the inline
  card's Upgrade button was a no-op and 403 showed "Failed to generate plan (403)").
  `FeatureLimitUpsellScreen` gained `notIncluded`/`unlockPoints` (no "0 of 0 used" card); the
  pre-check path in `MainScreen` passes `notIncluded` + server message and now deep-links to
  `"subscription"` rather than the Profile tab. Compiled clean.
- **iOS**: `FeatureAvailability` gained `notIncluded`/`reason` + `fromLimitError(status:body:)`;
  `FeatureLimitUpsellView` hides the usage/reset card and shows goal-oriented unlock points in

## 5c. AI runner profile ("What your coach knows about you") — account-age + km-unit fixes — DONE server

Reported: Chris (account 3 days old, three walks) got *"averages only 0.8 runs per week, with no
kilometers logged in the past month, highlighting a concerning trend of low engagement"* and was
being "tapered" for his "Walk daily" goal. Three root causes in `server/runner-profile-service.ts`:
1. **km unit bug** — `runs.distance` (kilometres) was divided by 1000, so every run read as
   `0.01km` and the 4-week volume as `0.0km/week`. Same bug in `session-coaching-service.ts`
   (pre-run recent-runs context) and `routes.ts` comprehensive-analysis (the stored
   `coachingObservations[].distanceKm`). New shared helper `server/utils/run-units.ts` →
   `runDistanceKm()` (TS twin of `DIST_KM` in user-stats-cache.ts) used at all three sites.
2. **No account-age context** — 4-week averages were divided by 4 regardless of account age, and
   the prompt never said when data starts. Now: `accountDataWindowNote(createdAt)` (exported;
   empty once ≥28 days old) heads the prompt, averages divide by `weeksObserved`, "Account created …
   data starts here" line, and both system prompts carry a DATA STARTS AT ACCOUNT CREATION rule.
   The same note + guidance is injected into the post-run analysis prompt
   (`generateComprehensiveRunAnalysis` gained `accountCreatedAt`, passed from both call sites) since
   its observations feed back into the profile.
3. Walks weren't labelled (`sessionType` now in the recent-runs lines as `WALK …`) and the
   imminent-goal "taper / race day" note fired for any goal with a date — now EVENT-type only.

**Data repair (already applied to Neon, and idempotent in `auto-migrate.ts` for the deploy):**
33 stored coaching observations across 6 users re-derived from their run rows. Six profiles that
were provably built on the `0.01km` data (Chris, sharkbait2035, daniel@better, mielmaclean,
clairej268, mohamad.khakpaki) were set to NULL so the next refresh writes a clean baseline —
`runnerProfileBlock(null)` is '' so nothing downstream breaks meanwhile. Profiles regenerate on the
next saved run / post-run analysis or via `POST /api/my-data/refresh-runner-profile`. Could not
regenerate from here: local `.env` has a placeholder `OPENAI_API_KEY`. The exact prompt Chris
would now get was captured via a fake fetch and reads correctly (WALK lines, real km, 2-day window,
no taper note).
