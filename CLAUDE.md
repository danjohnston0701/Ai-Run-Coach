## Repository shape

This is a monorepo with several independently-buildable pieces sharing one backend:

- **`app/`** — the production Android app (Kotlin, Jetpack Compose, MVVM, Hilt DI). This is the primary product surface.
- **`server/`** — Node/Express + TypeScript backend (Drizzle ORM, PostgreSQL/Neon). Serves the Android app, the Garmin/Samsung companion apps, and `client/`.
- **`client/`** — a Vite + React web app (wouter routing, shadcn/radix components, Tailwind) — landing page plus a web version of core run/profile flows. Not React Native despite RN packages listed in `package.json`; those are largely vestigial.
- **`shared/`** — dual-purpose: a Kotlin Multiplatform module (`shared/src/{commonMain,androidMain,iosMain}`, wired into the Gradle build via `settings.gradle.kts`) providing run analytics/coaching logic shared between Android and iOS, **and** `shared/schema.ts` — the Drizzle schema/Zod types imported by the server and web client as `@shared/*`.
- **`garmin-companion-app/`** — Garmin Connect IQ watch app (Monkey C).
- **`wear/`** — Wear OS (Kotlin/Compose) companion app for Samsung Galaxy Watch 4+, a standalone Gradle module with its own `applicationId`. Mirrors the Garmin Connect IQ app's screens/lifecycle; talks to the phone app via the Wear Data Layer (`SamsungWatchManager.kt` on the phone side) with a direct-HTTP fallback for standalone/offline use. Supersedes an earlier Tizen-based `samsung-watch-app/` scaffold (removed 2026-08-14, never went past initial scaffolding).
- **`migrations/`** — Drizzle-generated SQL migrations. Numerous one-off `ADD_*.sql` / `*.sql` scripts also live at the repo root from earlier ad-hoc schema changes — check `migrations/` first for the canonical history.

## Architecture notes

### Backend route registration
`server/index.ts` calls `registerRoutes(app)` from `server/routes.ts`, which is the main router (very large — thousands of lines) and also mounts feature-specific sub-routers as separate files, e.g. `routes-my-data.ts`, `routes-achievements.ts`, `routes-adaptation.ts`, `routes-samsung-companion.ts`, `routes-session-coaching.ts`. When adding a new feature-area of endpoints, prefer a new `routes-*.ts` file mounted in `routes.ts` over growing `routes.ts` further.

### Stats cache + self-heal pattern (`server/user-stats-cache.ts`, `server/my-data-service.ts`)
The "My Data" screen (personal bests, all-time totals) reads from a precomputed `user_stats` cache table (O(1) PK lookup) instead of scanning every run on each request. Two write paths keep it current:
- `onRunSaved(userId, run)` / `onRunDeleted(userId)` trigger a full `recomputeForUser(userId)` (always full recompute — incremental updates previously caused unit-conversion drift).
- Admin endpoints (`POST /api/my-data/reset-cache` for self, `POST /api/my-data/admin/recompute-all` for all users) exist for backfill/recovery after fixing cache-computation bugs.

Because the cache can go stale relative to the live computation logic (e.g. after a bug fix ships, existing cached rows aren't automatically corrected), `getPersonalBests()` in `my-data-service.ts` **self-heals on read**: it validates cached PB entries against the actual `runs` table (existence, and for distance-banded categories like 5K/10K/Half/Marathon, that the referenced run's logged distance genuinely falls in that band — not just that *some* run exists) before trusting the cache, falling back to a live query (`getPersonalBestsLive`) otherwise. When touching PB/stats logic, keep the cache-write path (`user-stats-cache.ts`) and the live-query/self-heal path (`my-data-service.ts`) in sync — divergence between them is exactly what produces fabricated-looking data.

### Subscription entitlement sync (`server/apple-server-notifications.ts`, `server/google-play-billing.ts`)
The DB (`users.subscription_tier/status/entitlement_type/entitlement_expires_at/ai_plans_enabled`) is the source of truth for access; clients only cache it. Both stores push lifecycle events server-side and both have a store-specific transactions table (`apple_transactions`, `google_play_transactions` — raw `pool` queries, not in the Drizzle schema) mapping store identifiers back to users:
- **Apple**: App Store Server Notifications V2 → `POST /api/apple/server-notifications`. `SUBSCRIBED`/`DID_RENEW`/`DID_CHANGE_RENEWAL_*` grant with the real renewal date; `EXPIRED`/`GRACE_PERIOD_EXPIRED`/`REFUND`/`REVOKE` clear the tier. Users are matched by `appAccountToken` (= `users.id`, set by StoreKitManager) then `original_transaction_id`.
- **Google Play**: `POST /api/subscriptions/verify-purchase` (Android, on purchase + every app start) verifies the token against the Play Developer API (`purchases.subscriptionsv2.get`, service-account auth via `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON`); RTDN Pub/Sub push → `POST /api/google/play-notifications` (`routes-google-play.ts`, optional `RTDN_SHARED_SECRET`) — treated as a hint, state is always re-fetched from the API; hourly reconcile in `scheduler.ts` is the safety net. Users are matched by recorded `purchase_token`, then `obfuscatedExternalAccountId` (= `users.id`, set by `BillingManager.setObfuscatedAccountId`), then `linkedPurchaseToken`. Without the service-account secret everything degrades to the old trust-the-client behaviour (logged as a warning) — so a "cancelled subscriber still has access" report first means checking that secret is set in Replit.
- Never clear a user's tier from one store's event unless their `entitlement_type` belongs to that store (`apple_*` / `google_play_*`) — promo/comped entitlements (`admin promo`, `comped_standard_30d`, …) and cross-store upgrades must survive.

### "Forgot to stop" end trim (`server/run-end-trim.ts`, `server/routes-run-end-trim.ts`)
End-of-run counterpart to the live start-line idle credit (Android `RunTrackingService.hasCreditedStartIdle`; ported to iOS 2026-09-28 as `RunSessionViewModel.hasCreditedStartIdle` in `HomeScreens.swift`, same thresholds, phone-led sessions only). It can't run live (a walk could be a walk break), so the server scans the saved GPS track for the last point at running pace followed by a ≥2 min walk/standstill tail that never returns to running, and the Run Summary (Android `EndTrimCard` in `RunSummaryScreen.kt`, iOS `EndTrimCard` in `RunSummaryScreen.swift`) **suggests** trimming — nothing changes until the runner taps Trim. The pre-trim columns are snapshotted in `runs.end_trim` (auto-migrated JSONB) so Undo restores them verbatim; "Keep as recorded" stores `{status:"dismissed"}` so the card never returns. Never applies to Garmin/watch/imported runs (watch data is source of truth). "Target achieved" gets a 1% GPS tolerance after a trim. AI insights text generated before a trim is not regenerated.

### Server-derived run columns (`server/utils/run-derivation.ts`, `server/run-derived-fields.ts`)
Only Android computes most run summary columns on-device. `storage.createRun` fills every still-NULL derivable column before the INSERT (terrain_type, steepest_incline/decline, elevation/difficulty, avg_speed, moving/elapsed_time, calories/active_calories, run_date/run_time in the user's timezone, ai_coach_enabled — never NULL, workout_type — never NULL, `"free"` outside a plan, name — `defaultRunName()`: the planned workout's name ("Tempo Run") else local time of day ("Morning Run"), mirrored client-side by Android `RunNaming.kt` / iOS `RunNaming.swift` for older unnamed runs (change all three together), struggle_points — `[]` = analysed/none, and `recording_source`: phone / apple_watch / garmin_watch / wear_os_watch / phone_apple_watch / phone_garmin_watch / phone_wear_os_watch / strava_import). Rules mirror Android's RunTrackingService; client values always win. An hourly sweep (`recording_source IS NULL`) covers runs inserted outside createRun (companion sessions, Strava) and history, and repairs time series stored as JSON strings (iOS sends every series as a string; POST /api/runs now parses them via `normalizeSeriesFields`). `"free"`/`"watch_standalone"` are `NON_PLAN_WORKOUT_TYPES` — never pass them to the AI as plan context. `start_time`/`end_time`/`max_incline_*` are legacy DB columns outside the Drizzle schema, written by type-aware raw SQL.

### User activity log (`server/user-activity.ts`, Neon table `user_activity`)
One row per key user action: `created_at, user_id, user_email, action, outcome (success|error), error_message, http_status, platform, app_version, details`. Server-side actions are logged automatically by `userActivityMiddleware` from its `RULES` route list (outcome from the reply: ≥400 or `success:false` = error, with the reply's error text) — when adding a user-facing endpoint worth tracking, add a rule there. App-only actions (prepared/started run with/without route, prepared run for watch, generated share video) are reported by the apps via `POST /api/user-activity` (`UserActivityReporter.kt` on Android, `APIService.reportUserActivity` on iOS, the run-video page itself) and must be listed in `CLIENT_ACTIONS`. Table created by `auto-migrate.ts`. Both apps send `X-App-Platform` / `X-App-Version` headers.

### Run-with-route navigation (`server/route-instructions.ts`, `RouteNavigator` on both apps, `tools/nav-sim/`)
Both apps generate routes via `POST /api/routes/generate-intelligent` (GraphHopper). `buildSpokenInstructions()` turns GraphHopper's raw instructions into runner-ready turns (drops name-change "continue"/via-point/finish entries, merges road-crossing jogs by net direction, chains turns < 60 m apart with "then …", no compass bearings) and emits `text`+`instruction`, `lat`/`lng`, `distance` (metres from the start — used to pin each turn to the right pass of a revisited spot) and `streetName`. The engine is `navigation/RouteNavigator.kt` (Android) with a line-for-line Swift port `RouteNavigator.swift` in the iOS project — change both together. `tools/nav-sim/generate-fixtures.ts` builds simulated runs on real OSM routes (clean / pavement offset + corner cutting / fast / slow / wide road / GPS-drift canyon / missed turn / wrong turn / shortcut); `RouteNavigatorSimulationTest` (Android, hard guarantees) and `tools/nav-sim/ios/run.sh` replay them, and `tools/nav-sim/evaluate.ts both` scores cue timing against the true position and compares the platforms. Advance warnings speak the literal instruction (Android: `/api/tts/generate` coach voice — never the LLM); time-critical cues use device TTS.

### Web live-run viewer (`client/src/pages/ObserveLive.tsx`, `GET /observe/:code` in `routes.ts`)
Every observer invite links to `https://airuncoach.live/observe/{code}`. That route serves the web app's `index.html` with this run's title and description in the link-preview tags. If there's no web build, it serves the old static "get the app" page instead. `ObserveLive` is the browser version of the apps' observer screen (Android `ObserverRunSessionScreen`/`ViewModel`): no login, a Leaflet map with the planned route, trail and runner, stats, the smoothed clock, the "may have lost signal" line, the coach card and the final numbers. It calls `GET /api/observe/{code}` **once**, because that endpoint is rate-limited to 10/min per IP+code. After that it polls `GET /api/live-sessions/{id}`: every 2 s while running, 3 s while waiting, 15 s when the tab is hidden. When the observer screen changes on the apps, change this page too.

### Unit conventions (see comments atop `server/user-stats-cache.ts`)
- `runs.distance` → kilometers; legacy rows may store meters (`distance > 200` is the on-the-fly detection heuristic used throughout the codebase). A Postgres trigger (`trg_runs_normalize_distance`, created by `auto-migrate.ts`, canonical SQL `migrations/20261009_runs_distance_rounding.sql`) rewrites every insert/update to 2 decimal places and snaps it up to the whole km when it's ≤ 0.03 short (3.97 → 4.00) — so whatever a client sends, the stored value can differ slightly; don't "fix" that in app code. `avg_pace` and splits are not recomputed from the snapped distance.
- `runs.duration` → **seconds**, not milliseconds.
- `pb_*_duration_ms` cache columns → milliseconds.
- `km_splits[].time` → milliseconds per split.

### Android networking
`app/src/main/java/live/airuncoach/airuncoach/network/RetrofitClient.kt` toggles between local dev backend and production (`https://airuncoach.live`) via a `useLocalBackend` flag; release builds always use production regardless of the flag.

### Android structure
Standard MVVM: `viewmodel/` (one per screen, Hilt-injected), `ui/screens/` (Compose screens) and `ui/components/` (reusable composables), `domain/model/`, `data/` (session/auth managers), `network/` (Retrofit services + DTOs), `service/` (foreground services, e.g. run tracking). Theming (`Colors.kt`, `AppTextStyles.kt`, `Spacing.kt`) lives under `ui/theme/`.

### Session coaching plan generation (`session_instructions` / dynamic coaching plan)
Each planned workout's AI coaching plan (phases, triggers, pre-run brief) is generated **on-demand only**, the first time it's actually requested — `POST /api/workouts/{id}/prepare-coaching` → `getOrGenerateSessionCoaching()` in `server/session-coaching-service.ts` — then cached on `planned_workouts.session_instructions_id`, version-gated via `CURRENT_PLAN_VERSION` in that file (bump it when prompt/trigger logic changes, to force regeneration of stale cached plans on next open).

`server/session-enrichment-service.ts`'s `enrichWorkoutBlock()` does **not** eagerly regenerate coaching plans for every workout in a block anymore — its `regenerateCoaching` param defaults to `false`. Only `server/scheduler.ts`'s daily rolling-enrichment cron opts in with `true`, since that's the only call site where a workout could already have a stale *cached* plan from an earlier open that genuinely needs refreshing; new-plan-creation, next-block-generation, and post-orientation-enrichment call sites have no prior cache to go stale, so forcing regen there was pure wasted OpenAI cost. Keep new call sites defaulting to `false` unless they can hit an already-cached workout.

Android (`WorkoutDetailScreen.kt`) reflects this: it shows a full-screen "Generating your full session" loading view — not the detail screen with a banner — until `RunSessionViewModel.coachingGenerationState` reaches READY or FAILED, and keeps Start/Prepare-for-Watch locked through `isAudioPreloading` (Polly TTS pre-caching, which finishes *after* the plan itself) too, not just until the plan JSON arrives. `WorkoutStructureSection` renders from the real generated `DynamicCoachingPhase[]` (`activeSessionCoachingPlan.phases`), not a hardcoded per-workout-type template — don't reintroduce a static fallback there, it will drift from what the AI actually generated (confirmed: a hill-repeats session UI once showed a fabricated 10-min warm-up that didn't exist in that session's real data).

`ensureClosingStageMilestones()` in `ai-service.ts` guarantees a `session_complete` trigger exists even if OpenAI's response omits one, for both distance-based (`distance >= X`) and time-based (`elapsed_min >= X`) sessions — the time-based fallback is a relatively recent addition, so don't assume every historically-cached plan has one (cache version gate will regenerate them, but only on next open past a version bump).

### AI plan quality gate (`server/plan-quality.ts`)
Every plan block (`generateTrainingPlan` and `generateNextBlock`) goes through this gate before it is saved, at every fitness level. Novice and injured runners also keep their stricter time-based rules (`findProgressionViolations`).
- **Starting point:** weekly volume and longest run come from the last 30 days of runs, measured over the span actually recorded. With fewer than 3 runs it combines those with what the stated fitness level means (`LEVEL_BASELINES`, taken from the apps' own level descriptions). Never invent a figure.
- **Pace anchor:** the best effort of 3 km or more is projected to a 5K (Riegel) and gives the easy, tempo and interval pace bands.
- **The rules** (`buildLoadRulesPrompt`, checked by `findLoadViolations`):
  - Week-1 and week-on-week volume caps.
  - Long-run growth cap and a long-run floor.
  - The long run is the longest session of its week.
  - No walk-run for runners who already run continuously.
  - Minimum session length.
  - Never three running days in a row, across week boundaries too.
  - At most 2 quality sessions a week.
  - Deload weeks are lower in both volume and long run.
  - Tempo/threshold is Zone 4.
- **Enforcement:** the model gets two correction rounds, then `repairPlanLoad` fixes whatever is left.
- **Enrichment** (`session-enrichment-service.ts`) uses the same anchor to clamp paces and the same category to set HR zones.
- **Regular sessions** (club runs) the runner lists count toward their starting volume and stay on their own day (rule 9, `fixedSessions`).
- **Volume cap floor:** the weekly cap never drops below n − 1 thirty-minute runs plus the long-run floor, so the trim can't undo the minimum session length.
- **Max HR:** run peaks can only raise the age estimate (`estimateMaxHR`, `HeartRateZones.estimateMaxHRFromHistory`). An easy-only runner's peak isn't their max.
- **Runs from anywhere count** (`server/plan-run-sync.ts`): every run — app, free run, Strava webhook/import — first completes a pending orientation, then an open session on the same date. Runs paced outside 3:00–20:00/km don't count.
- **Stalled plans:** if the orientation is never done, weeks 1–2 are enriched from history 2 days after its date. Sessions whose date has passed are never enriched.

- **Orientation first** (`server/plan-orientation.ts`, 2026-11-23): a runner with no history gets an orientation run as the first session they'll actually see. Week-1 days already past are dropped at save, which used to drop the AI's orientation (Jade's plans made on a Sunday started with a 7 km long run, and every session waited for targets "once your orientation run is complete", forever). `ensureOrientationFirst` converts the first kept session if needed. **First session day:** tomorrow unless the runner picks "today" on the generate screen (`firstSessionStart`; "flexible" also means from tomorrow, and Android now defaults to tomorrow like iOS). The server enforces it at save (`firstAllowedDayIdx`), not just in the prompt. A plan made on a Sunday with "tomorrow" starts week 1 on Monday (`weekShiftDays`), and plan details report week 1's Monday as `plan.createdAt` (`planWeekOneAnchor` in `routes.ts`), because both apps count weeks from that field — so installed apps show the right week too. The real creation time stays in the DB. Plans saved before this get weeks 1–2 enriched from the first real run (`calibratePlansWithoutOrientation`) or, with no run, 2 days after their first session (the stalled-plan sweep).
- **The goal informs the plan** (`server/plan-goal-match.ts`, 2026-11-23): a plan without a goalId is matched to the runner's active goal of the same distance whose date hasn't passed (not one already driving another active plan; race-dated first). Its event name and notes reach the prompt. A race within `MAX_RACE_PLAN_WEEKS` (20, the apps' longest plan) sets the length so the plan ends in the race week (`weeksToRace`, counted from week 1's Monday; beats the app's `durationWeeks`) and fills in the goal's target time. A race further out does **not** (Daniel: runners keep a plan 6–10 weeks, so it must stay relevant): the runner's chosen length stands, no target time, and the prompt treats the race as a long-term goal (`longTermGoalNote`, the "first phase" plan type: base and habit, no peaking/taper, no need to reach the distance, a realistic end-of-plan milestone). Both apps call `GET /api/plan-goal-match`: "Ends on race day" replaces the length slider for a near race (Android `RaceDayCard` in `GeneratePlanScreen.kt`, iOS `raceDayCard` in `GeneratePlanScreen.swift`); a far one shows "Working towards your goal" and "Your race is N weeks away…". Before this neither app ever sent a race date.
- **HR zones need a heart-rate source** (`server/hr-source.ts`): a run with HR, a Garmin watch app seen, an active Garmin/COROS/Samsung/Apple device link, or an app reporting a paired watch (`hasHeartRateDevice` on plan generation → `users.heart_rate_device_reported_at`, auto-migrated). A Strava link alone isn't one. Without one, plan generation and enrichment store no zone/BPM and the prompts say effort only; the apps show effort instead of zones (Android `WorkoutDetailScreen` gates on the server zone, iOS already did). Zones arrive at the next enrichment once a source exists.
- **Height** is centimetres, 100–250 only: `PUT /api/users/:id` ignores anything else, and both apps' Personal Details take cm or ft + in (Android `utils/HeightUnits.kt`, iOS `HeightUnits` in `WeightUnits.swift`) and ask the runner to re-enter a saved height outside that range.
- **Novice rest days:** ≤3 days/week never back to back; 4 days/week at most one back-to-back pair per week, never three in a row (Sunday → Monday counts). `repairNoviceSpacing` fixes what the model doesn't — the old "rest day after every session" rule was impossible at 4 days/week.
- **Review pass** (`server/plan-review.ts`): after the rules, a coach-style read checks each session's text against its own numbers, level and goal. It may only rewrite description/instructions — never distances, paces, zones, days. `PLAN_AI_REVIEW=0` turns it off.
- **Missed a week** (`server/plan-stall.ts`, daily 5:50 UTC): runner quiet 7+ days (but active in the last 28) with a session a week overdue → open sessions from that week on move back a week, next block too, and the runner is notified. Race-dated plans absorb the week by generating one fewer. Next-block dates anchor on the latest week for this reason.
- **AI provider** (`server/plan-ai.ts`): every plan AI call (block 1, next block, corrections, enrichment, adaptation, reassessment, review) goes through `planChat`. `PLAN_AI_PROVIDER=anthropic` switches all of them to Claude (`CLAUDE_PLAN_MODEL`, needs `ANTHROPIC_API_KEY`); default OpenAI. Overrides, first match wins: `PLAN_AI_PROVIDER_WAITING_<TASK>` / `PLAN_AI_PROVIDER_WAITING` (only while an older app waits on a one-request plan), then `PLAN_AI_PROVIDER_<TASK>`.
- **Background plan creation** (`server/plan-jobs.ts`, table `plan_generation_jobs`, auto-migrated): a Claude plan takes ~2–2.5 min, past the apps' request timeouts (iOS 90 s, Android 120 s). Apps that send `async: true` (Android 2.0.67+, iOS after the matching build) get `202 {jobId}` and poll `GET /api/training-plans/jobs/:jobId` (generating → ready + planId | failed + error) every 3 s; a second tap gets `429 PLAN_GENERATION_IN_PROGRESS` with the running `jobId`. Jobs are in the DB because autoscale may answer a poll from another instance; one still generating after 8 min is reported failed. Older apps keep the one-request path (`whileRunnerWaits`). The server also accepts iOS's field names (`targetTimeSeconds`, `linkedGoalId`, `is_pre_event_plan`) — they were silently ignored before.
- **Comparing engines/rule changes:** `tools/plan-compare/compare.ts` generates plans for real runners on a Neon BRANCH (refuses the `.env` database) and records first-attempt rule breaks, corrections, repairs, review rewrites, time and cost; `report.ts` builds the side-by-side page.

When a reviewed plan is wrong, add the missing rule here, not a prompt patch.

### Free-trial plan cap (`server/plan-trial-cap.ts`)
A plan made on the free trial is generated only far enough to hold its first `TRIAL_PLAN_SESSION_CAP` (4) non-rest sessions (`trialWeeksToGenerate`: 2–3 weeks, one spare for a short week 1). Sessions after those are locked, and the next block isn't generated (`generateNextBlock` returns early while `isPlanCapped`). `training_plans.trial_session_cap` holds the cap (auto-migrated; NULL = full plan).
- **Lifting:** once the runner has AI Plans (paid tier with AI Plans, or a promo grant: `userHasAiPlans`), the next plan read or app-start block check lifts the cap: an atomic `UPDATE … WHERE trial_session_cap IS NOT NULL` claim, then the rest is generated. There's no hook in the store paths; the lazy lift covers both.
- **Enforced on the server:** prepare-coaching returns 403 `plan_session_locked`; runs never complete a locked session (`plan-run-sync.ts`); `open-today` never offers one. Plan details return a per-workout `locked` flag and a `trialCap` summary, and today's workout carries `locked`.
- **App versions:** only apps that send `supportsTrialCap` (Android 2.0.81+, iOS after 2026-11-18) can create a trial plan. Older apps get the old "not in the free trial" 403.
- **Allowances:** trial plans (1), routes (5) and one-off sessions (4) count across the whole trial (`WHOLE_TRIAL_FEATURES` in `usage-service.ts`), not per month; `GET /api/features/:f/available` returns `period: "trial"` for them and words its message "during your free trial". AI coaching km and run summaries stay monthly. The trial lists on both apps (onboarding subscription screen, subscription Free Trial card, free-trial promise) mirror `TIER_LIMITS.free`; change them with it.
- **Today's session** (`GET /api/training-plans/:id/today`) offers a locked session only once no free one is left open; a missed free session comes back as overdue.
- **After the lift:** plan details return `generatingNextBlock` (true on the read that lifts the cap, then while `training_plans.next_block_generating_at` is set) and the apps show "Building the rest of your plan" and reload every 5 s. `generateNextBlock` claims that column atomically (10 min stale), so autoscale instances can't build the same weeks twice; the app-start check passes `onlyIfDue` so it never builds the block after one that just finished.
- **Apps:** Android `ui/components/TrialPlanCap.kt` and iOS views at the end of `CoachingPlanScreens.swift` (banner, locked rows, locked-week placeholders, locked today card; every tap opens the subscription screen). Change them together.

### Progress check-ins: on time or not at all (`utils/ProgressMilestones.kt`, iOS `ProgressMilestones.swift`)
The free-run 25/50/75% check-ins and any coaching-plan trigger keyed on `distance_pct` ("halfway_milestone") get a short window just past their point (~8 s of travel, 20–50 m). They fire inside it only when nothing is playing, queued or being generated, and are skipped once it closes. The generated audio must also come back within 8 s and find the slot still clear (`deliverIf` gate on `fireEliteCoaching` / `fireLiveTriggerMessage`, and on iOS `executeEliteCoaching` / `fireDynamicCue`), or it's dropped. Don't put them back into the elite cooldown chain or let them queue: that's what produced "halfway" at 60% and "25%" at 1.4 km of 3 km. Milestones on a km marker go to the km split, ones inside the final 500 m to the finish cues. The two files are line-for-line ports, so change both together.

  - **AI Coaching Settings screen structure**: onboarding shows coach personality (name/voice/accent/tone) and coaching-trigger prompts (pace/HR/cadence/km-split interval/etc.) as **two separate screens** (`CoachSettingsScreen` → `InSessionCoachingSettingsScreen` on Android; `CoachSettingsScreen` → `CoachingPromptsSettingsScreen` on iOS). The **profile's** "AI Coaching Settings" entry point shows **both sections consolidated into one screen** instead — this was broken on both platforms after the onboarding split (profile was left pointing only at the personality screen, losing the trigger toggles entirely) and has been fixed on both: Android's `CoachSettingsScreen.kt` now renders the trigger-toggle section inline when `isOnboarding == false`; iOS's `CoachSettingsScreen.swift` had the equivalent `coachingToggles` view already written but never called from `body` — now wired in the same way.
  - **Account Management** (profile → My Account → Change Password / Get Support / Delete Account): all three now work end-to-end on both platforms. Delete Account sends a notification to `support@airuncoach.live` with the user ID + email so it can be actioned against Neon manually. iOS's Get Support was rebuilt as an in-app form (`GetSupportScreen.swift`) matching Android's, replacing a dead external web link.
  - **iOS-only fixes discovered during a Dashboard/My Data parity audit** (`Dashboard.swift`/`DashboardModels.swift`/`MyDataScreen.swift`, none of which have an Android-side equivalent bug):
    - **Data-loss bug (fixed)**: a live run could be silently killed by swiping back from the screen edge — `RunSessionViewModel` was a plain per-screen `@StateObject` with no persistence and the run screen only hid the nav-bar back *button* (`.toolbar(.hidden, for: .navigationBar)`), not the interactive edge-swipe gesture. Fixed with a `disableSwipeBack(_:)` `UIViewControllerRepresentable` helper (`AppTheme.swift`) active whenever `vm.isRunning`.
    - Same investigation led to `RunSessionViewModel.activeInstance` — a static reference set/cleared alongside the run's real start/stop (`startRun()`/`stopRun()`/`cancelRun()`), used so `RunSessionScreen` reattaches to an already-running session (`RunSessionViewModel.activeInstance ?? RunSessionViewModel()`) instead of always constructing a fresh one, and so `DashboardViewModel` can poll it to drive a working "Resume Run" banner (previously dead — `activeRunSession` was declared but never assigned). Every setup path that would otherwise re-run on top of a live session (`onAppear`'s config block, `tryBeginRunIfReady`) is now guarded behind `!vm.isRunning`. **Needs real on-device testing** (start a run → background/return to Dashboard → confirm live Resume banner → tap Resume → confirm it reattaches to the *same* session rather than restarting blank → finish normally → confirm the next run starts clean) — this could not be compile- or interactively-verified in this environment; treat as unconfirmed until tested.
    - Weather silently fell back to fabricated London coordinates when location permission was denied instead of showing "no data" like Android — fixed.
    - The Dashboard Goal card didn't exclude abandoned goals (only filtered `!isCompleted`, missing `isActive`) despite iOS's own `Goal` model already computing `isActive` correctly — fixed.
    - My Data's "Exclude AI Coaching Plan runs" toggle was fully non-functional (visible, defaulted on, but the backend had zero support for the `excludeCoachingPlan` query param) — now genuinely implemented across `getPersonalBests`/`getPeriodStatistics`/`getDetailedTrends`/`getAllTimeStats` in `server/my-data-service.ts`, each defaulting to whatever Android already got before this change (so Android behavior is unaffected).
    - `/api/my-data/trends` (the endpoint iOS's period selector hit) ignored its `period` query param entirely and always returned a hardcoded 30-day window — iOS's period picker (1M/3M/6M/1Y) did nothing. Redirected iOS to `/api/my-data/detailed-trends?days=X`, the endpoint Android already uses correctly; left the `/trends` route itself as-is (unused by either client's current code, not worth touching further).
- **Garmin-watch-initiated walk session freeze — still open, unconfirmed root cause.** Starting a walk session from the watch froze the timer within seconds; Garmin Connect saved 3 separate short activities instead of one continuous session. `garmin-companion-app/source/views/RunView.mc`'s `_startSession()`/`onShow()` has a defensive comment acknowledging this exact failure mode, and two recent watch-side commits touch the relevant walk-only branches — plausible but unconfirmed. Needs an on-device crash log or simulator repro with debug logging before attempting a fix.
- **Strava integration returning 403s** — traced to `{resource:'Application', field:'Status', code:'Inactive'}` from Strava's own API, an account-level status flag on the Strava Application in Strava's developer dashboard, not a code bug. `server/strava-oauth-bridge.ts` logs the real Strava response body on import failures — check that log next time this comes up.
